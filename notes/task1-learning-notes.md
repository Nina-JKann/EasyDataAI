> 记录日期：2026-11-16

## 一句话结论

模型决定 AI“能想多好”，数据决定 AI“能做多好”。使用 AI 时，遇到效果问题应先判断数据缺了什么，再判断是否需要更换模型。

可以把三课串成一条完整链路：

```text
F0：用一个真实产品展示数据飞轮
      ↓
F1：解释模型为什么会缺少事实、时效和个性化数据
      ↓
F2：把数据需求落到 Agent 的记忆、检索和工具架构上
```

## 一、F0：Agent 为什么会“越用越好用”

### 1. 我读懂了什么

OpenClaw 越用越好用，关键不只是模型更强，而是它在持续积累与使用者有关的数据。

它的核心运行机制可以概括为：

```text
对话前读取相关数据
      ↓
基于数据完成任务
      ↓
把偏好、经验、错误和规则写回数据文件
      ↓
更新检索索引
      ↓
下一次对话表现更好
```

这构成一个不断循环的数据飞轮。

OpenClaw 用一组 Markdown 数据文件承载不同种类的经验：

| 数据文件 | 承载内容 | 我的理解 |
|---|---|---|
| `SOUL.md` | Agent 的人格、语气和价值边界 | 规定“它是谁” |
| `USER.md` | 用户习惯、偏好和背景 | 规定“为谁服务” |
| `AGENTS.md` | 工作规范与踩坑记录 | 记录“事情该怎么做” |
| `TOOLS.md` | 工具、路径、主机等环境信息 | 记录“在什么环境中做” |
| `SKILL.md` | 特定领域的操作手册 | 把专业经验变成可复用技能 |
| `memory/*.md` | 按天记录的交互内容 | 保存“近期发生了什么” |
| `MEMORY.md` | 从日常记录中提炼的长期信息 | 保存“真正值得长期记住的内容” |

这些文件并不只是存储介质。它们真正的作用是：**把一次对话中获得的经验，转化为未来对话可以再次使用的上下文。**

### 2. 三个值得记住的判断

1. **Agent 的独特价值主要沉淀在数据里。**

   代码和基础模型通常可以复制，但用户偏好、业务规则、失败记录和高质量技能属于长期积累。两个团队使用同一个模型，最终效果不同，往往是因为各自积累的数据不同。

2. **“培训 Agent”本质上是在整理数据。**

   不需要每次都重新解释规则。把稳定流程写进 `SKILL.md`，把错误写进 `AGENTS.md`，把用户偏好写进 `USER.md`，这些数据会在后续任务中持续发挥作用。

3. **数据积累也会带来上下文和治理问题。**

   文件越多，不代表效果一定越好。过期信息、相互冲突的规则和无关记忆会占用上下文，甚至污染模型判断。因此，记忆不只是“保存”，还包括提炼、检索、更新和遗忘。

### 3. 我打算怎么用

- 每完成一次重要任务，不只保留聊天记录，还提炼一条可复用的经验，记录到自己的学习仓库中。
- 为不同项目建立独立的知识区域，避免代码、写作和数据分析的经验互相干扰。
- 把“以后都这样做”的稳定要求写成明确的规则或模板，而不是每次临时解释。
- 把错误和修正一起记录下来，形成自己的“踩坑清单”和任务检查表。
- 定期清理过时规则，给记忆设置清晰的边界，避免仓库逐渐变成无法维护的信息堆。
- 从 GitHub 输出角度，用 Markdown 管理笔记、模板和复盘，使每次修改都有历史记录，也便于后续搜索和复用。

## 二、F1：大模型的三个边界，本质是缺数据

### 1. 我读懂了什么

大模型不是在检索事实，而是在根据概率逐个预测下一个 Token。它生成的是“统计上合理的文本”，不是天然经过核验的答案。

| 局限 | 典型表现 | 根本原因 | 解题方向 |
|---|---|---|---|
| 幻觉 | 答案听起来很合理，但事实错误 | 缺少可验证的事实数据 | 提供知识库并要求基于资料回答 |
| 知识截止 | 不知道最近发生的事情，或给出过时答案 | 缺少实时数据 | 接入最新数据源、搜索或业务系统 |
| 个性化盲区 | 回答正确但很泛，不符合用户和业务语境 | 缺少用户数据与业务数据 | 建立用户画像、业务规则和记忆系统 |

三个问题看起来不同，但共同根因是：

> **大模型只有内置训练数据，没有“你的数据”。**

因此，“回答不好就换模型”经常不是有效解法。更好的诊断方法是先补充数据，再观察效果。

一个很实用的实验是：

1. 找一个 AI 回答错误或过于空泛的问题。
2. 把回答问题所需的正确资料直接贴进对话。
3. 再让模型回答。
4. 如果加上资料后答案明显改善，说明主要瓶颈在数据，而不一定在模型。

延伸阅读还说明了 Token 和上下文窗口的意义：模型一次能处理的信息量有限，新的对话也不会自动继承上一次对话的内容。因此需要 RAG、记忆系统和 Agent 架构，有选择地把相关资料放进当前上下文。

### 2. 我打算怎么用

- 以后遇到 AI 回答不满意时，先做“三层排查”：
  1. 缺的是事实数据吗？
  2. 缺的是最新数据吗？
  3. 缺的是用户、业务或项目上下文吗？
- 在要求模型分析或写作时，主动提供必要的背景、约束、参考资料和合格示例，而不是只给一个目标。
- 对重要结论要求标注依据，并把事实核验与文本生成分开处理。
- 对时效性任务优先接入实时数据或主动搜索，不依赖模型训练时的知识。
- 记录每次效果提升来自“换模型”还是“补数据”，用实际结果验证判断，避免凭感觉认为新模型一定更好。
- 后续学习 RAG、Memory 和 Skill 时，重点观察它们分别在补哪一类数据，而不是只记工具名称。

## 三、F2：Agent 是一套处理数据的循环系统

### 1. 我读懂了什么

F2 给出了 Agent 时代的扩展公式：

```text
AI Agent 能力上限 = 模型能力 × 数据质量 + 流程编排
```

其中，乘号表示数据和模型共同决定基础能力量级；加号表示流程编排可以提升稳定性、可控性和执行效率，但无法突破数据和模型本身的上限。

Agent 不是“一次性生成答案的聊天机器人”，而是在循环中完成任务：

```text
感知 → 推理 → 行动 → 观察 → 再推理 → ……
```

这个推理与行动交替的过程通常称为 ReAct：

```text
Reasoning → Acting → Observing → Reasoning
```

例如“分析上个月销售增长原因”时，Agent 可以依次查询销售数据、分析变化、查找营销活动、交叉验证，最后生成报告。它通过多轮“行动 + 观察”获得新数据，而不是一次猜出完整答案。

Agent 的核心组件包括：

- **LLM**：负责理解、推理和决策。
- **Memory**：保存用户偏好、历史经验和长期规则。
- **Planning**：分解任务、安排步骤和选择策略。
- **Tool Use**：调用数据库、API、文件或外部系统。

### 2. 常见 Agent 能力的数据本质

| 能力 | 表面作用 | 数据本质 |
|---|---|---|
| RAG | 查询外部知识 | 知识数据的检索 |
| MCP | 连接和调用外部工具 | 数据接入的标准化 |
| Skill | 按固定方法完成某项任务 | 经验数据的结构化 |
| Memory | 记住用户和历史 | 数据的积累与召回 |

这张映射表是 F2 最值得保留的认知工具。它说明 RAG、MCP、Skill、Memory 并不是互不相关的热词，而是在 Agent 系统的不同位置处理数据。

几个具体理解：

- **RAG** 的效果取决于知识库质量、文档切分、检索策略和 Embedding。检索本身做得再好，也无法弥补知识库中没有正确资料。
- **MCP** 把工具接入从 \(M \times N\) 种适配关系简化为 \(M+N\)：工具提供统一 Server，Agent 使用统一 Client。
- **Skill** 把人的工作流程、领域规则、案例和术语显式化为可复用数据。
- **Memory** 需要同时解决“记住什么、怎么召回、何时遗忘”，不能只理解为保存聊天历史。

### 3. 我打算怎么用

- 给自己当前使用的 AI 工具画一张能力地图，逐项检查：
  - 有没有外部知识检索？
  - 有没有用户记忆？
  - 有没有稳定的技能或流程模板？
  - 有没有安全、标准化的外部工具接入？
- 对每项缺失能力继续追问：
  - 数据根本不存在？
  - 数据存在，但检索不到？
  - 数据结构不适合当前任务？
- 设计 AI 应用时，先定义需要哪些数据以及数据从哪里来，再选择 RAG、Memory、Skill 或 MCP。
- 用 Workflow 保证固定流程的稳定性，在需要开放探索时使用 ReAct 式循环，避免把所有任务都强行做成同一种架构。
- 建立任务执行记录，包括输入、检索到的数据、工具调用、输出和人工修正，为后续复盘提供证据。
- 学习路线先完成公共基础，再根据工作角色选择：
  - 产品与决策路线：P1 → P5。
  - 开发与工程路线：D1 → D5。

## 四、三课合起来形成的思考框架

以后面对一个 AI 效果问题，可以按下面的顺序判断：

```text
1. 现象是什么？
   幻觉 / 过时 / 回答太泛 / 无法执行任务
        ↓
2. 缺的是哪类数据？
   事实数据 / 实时数据 / 用户与业务数据 / 工具数据 / 经验数据
        ↓
3. 数据在哪里断掉了？
   不存在 / 存了但取不到 / 格式不适合 / 上下文塞不进去 / 流程不稳定
        ↓
4. 选择补数据的方式
   RAG / Memory / Skill / MCP / Workflow
        ↓
5. 验证效果
   比较补数据前后的结果，记录成功和失败案例
```

这套框架的核心不是记住几个技术名词，而是建立一种稳定的归因习惯：

> 先问“缺什么数据”，再问“用什么架构补”，最后用结果验证。

## 五、我接下来会完成的三项练习

### 练习 1：完成一次数据归因

找一个最近回答不理想的 AI 问题，判断它缺少事实数据、实时数据还是个人/业务数据。把正确资料补充进去后重新提问，并记录：

- 原问题与原回答；
- 识别出的数据缺口；
- 补充了什么数据；
- 新回答是否改善；
- 这次改善证明问题主要在哪一层。

### 练习 2：画一张能力地图

选择一个常用的 AI 产品或自己的工作项目，标记它是否具备 RAG、Memory、Skill 和 MCP，并注明每项能力的数据来源。

### 练习 3：建立可复用的数据资产

创建以下最小目录，不再只保存散落的聊天截图：

```text
notes/
├── task-notes/       # 课程学习笔记
├── playbooks/        # 可复用流程与 Skill
├── lessons-learned/  # 错误、修正和踩坑记录
└── projects/         # 各项目背景、决策与复盘
```

每完成一个课程任务，就同步更新：

1. 本任务学到的核心观点；
2. 可以迁移到实际工作的做法；
3. 仍未理解的问题；
4. 下一次需要验证的实验。

## 六、自测：我是否真的读懂了

- 为什么说幻觉、知识截止和个性化盲区，本质上是同一个问题？
- 为什么“换一个更强的模型”不能自动解决缺少实时数据的问题？
- 如何用一个简单实验判断问题更可能出在模型层还是数据层？
- Agent 的 ReAct 循环和普通聊天机器人的单次响应有什么区别？
- 为什么公式中是“数据 × 模型”的乘号，而流程编排使用加号？
- RAG、MCP、Skill、Memory 分别在 Agent 中处理什么数据？
- Agent 越用越好用时，哪些数据值得保留，哪些数据需要定期清理？

如果能够不看笔记回答以上问题，并完成一次真实的数据归因实验，就达到了 Task 1 的学习目标。

# Task 2 学习笔记：从场景判断到可执行 Agent

> 课程：Easy Data x AI  
> 学习内容：P1《AI Agent 场景识别》、D1《大模型 API 基础》、I1《AI 原生数据库基础》  
> 记录日期：2026-11-20

## 一句话结论

一个可靠的 Agent 项目要连续回答三个问题：

1. **值不值得做？** 看场景、数据和成功标准；  
2. **怎么让它做事？** 用 API、Streaming 和 Tool Use 建立执行循环；  
3. **怎样长期做对？** 用可靠的数据库保存事实、权限、状态和检索证据。

三节课分别对应产品判断、工程实现和数据底座：

```text
P1：选对场景，避免过度工程化
        ↓
D1：让模型调用工具，把“会说”变成“会做”
        ↓
I1：让事实可查询、证据可追溯、状态可恢复
```

---

## 一、P1：先判断值不值得做 Agent

### 1. 三种常见但不该用 Agent 的场景

- **固定答案 FAQ**：退款政策、Wi-Fi 密码这类问题，用页面、搜索或规则系统更稳定。
- **结构化数据查询**：GMV、客户数、日活趋势更适合 BI 看板或预定义 SQL。
- **高精度计算**：税费、利息等任务应交给确定性程序，模型最多负责理解输入。

核心判断不是“能不能做出来”，而是“有没有为了 AI 而增加复杂度、成本和不确定性”。

### 2. 三维度可行性评估

| 维度 | 核心问题 | 验证方法 |
|---|---|---|
| 数据可得性 | Agent 需要的答案和业务数据是否存在、准确、可接入？ | 列出 10 个典型问题，逐个寻找答案数据 |
| 任务可定义性 | 什么叫“做对了”？能否衡量事实正确性和输出质量？ | 找事实锚点、历史问答对、合格样本 |
| 流程编排 | 应该完全自主，还是使用人设计好的 Workflow？ | 看任务确定性、数据分散程度和错误代价 |

三个维度中，**数据可得性最重要**。课程用一个很直接的规则判断项目是否到了开发阶段：

> 10 个典型问题中，超过一半找不到答案数据，应先建设数据，而不是继续优化模型。

### 3. 任务可定义性为什么变难了

传统软件是确定输入、确定输出；LLM 的同一个事实可以产生很多种合理表达。因此评价困难不只来自“答得够不够好”，还来自：

- 哪些表达可以接受；
- 事实是否正确；
- 引用是否支持答案；
- 没有证据时是否会拒绝回答。

有事实锚点的任务，例如物流状态、用户反馈原文，可以用正确率、召回率、引用命中率验证。没有唯一答案的营销创意，则要建立人工评分、盲测或 A/B 基线。

### 4. Agent 与 Workflow 的边界

- **Agent**：用户给模糊目标，由模型决定下一步、调用什么工具和何时结束，适合开放任务。
- **Workflow**：人预先定义步骤和输入输出，AI 只负责其中需要语义理解的环节，适合流程稳定、错误代价高的任务。

选择顺序建议是：

```text
任务确定性高、错误代价高、数据分散
→ 优先 Workflow

任务开放、需要多轮探索和工具组合
→ 再逐步增加 Agent 自主性
```

很多成功的 AI 产品不是完全自主 Agent，而是 Copilot、Human-in-the-loop 或“简单任务自动处理、复杂任务转人工”的混合模式。

### 5. Agent 的三个甜区

- 用户意图模糊，需要理解、澄清和拆解；
- 任务需要调用外部工具或 API 才能完成；
- 任务需要多轮交互，并依赖前文上下文。

至少要命中其中一项，才值得考虑 Agent；三项都固定、答案又确定时，传统系统通常更合适。

### 6. P1 的实际用法

立项前用一页纸回答：

```text
目标用户是谁？
要解决什么模糊任务？
10 个典型问题的答案数据在哪里？
成功由哪些客观事实和主观指标共同判断？
哪些步骤必须由人审批？
第一版为什么需要 Agent，而不是 FAQ、BI 或 Workflow？
```

回答不了这些问题时，继续写 Prompt 或更换模型通常没有意义。

## 二、D1：用 API 和 Tool Use 让模型真正做事

### 1. 对话的本质是一个消息列表

模型本身不会自动记住上一轮。每次请求都需要重新发送完整历史：

| 角色 | 作用 |
|---|---|
| `system` | 规定角色、边界、行为规则和输出要求 |
| `user` | 用户当前的输入 |
| `assistant` | 模型此前的回答 |

所以“多轮对话”不是模型拥有永久记忆，而是应用在维护消息历史。历史越长，消耗的上下文和 Token 越多，因此后续需要记忆提炼和检索。

### 2. Streaming：优先改善首 Token 延迟

`invoke()` 等完整回答生成后再返回；`stream()` 则在第一个 Token 生成后就开始输出。

用户对等待的感知主要来自：

```text
点击发送 → 长时间没有反应 → 回答突然出现
```

流式输出把体验变成：

```text
点击发送 → 很快看到首个 Token → 持续生成
```

面向用户的生产应用通常应默认使用 Streaming；生产代码优先考虑异步 `ainvoke()` 和 `astream()`。

### 3. Tool Use 是聊天机器人和 Agent 的分界线

模型不能真的上网、查库或调用 API。Tool Use 的完整循环是：

```text
定义可用工具
    ↓
模型判断是否需要工具，返回 tool_calls
    ↓
应用代码执行工具
    ↓
用 ToolMessage 把结果返回模型
    ↓
模型继续推理或生成最终回答
```

最重要的分工是：

> **模型负责判断和选择，应用代码负责执行和授权。**

工具由应用定义，数据由应用获取，结果也由应用控制。模型并不能绕过应用直接操作系统。

### 4. 工具调用的工程要点

- 用 `@tool` 定义 Python 函数；
- 函数名是工具名；
- 类型注解生成参数结构；
- docstring 告诉模型**什么时候使用**这个工具；
- `bind_tools()` 把工具绑定到模型；
- 检查 `response.tool_calls`；
- 把工具结果包装成 `ToolMessage` 并传回；
- 循环直到没有新的 `tool_calls`；
- 设置最大轮数，避免无限调用。

如果模型一直不调用工具，常见原因是工具描述不够具体，模型不知道什么情况下该用。

### 5. 从手动循环到 Agent 框架

D1 的示例逐步演进：

| 示例 | 建立的能力 |
|---|---|
| `d1_1` | 单次模型调用 |
| `d1_2` | 手动维护多轮消息 |
| `d1_3` | 流式输出 |
| `d1_4` | Tool Use 手动编排，使用模拟数据 |
| `d1_5` | Tool Use 连接真实检索数据库 |
| `d1_6` | 交给 Agent 框架执行 ReAct 循环 |

`create_agent` 并没有改变底层原理，它只是把“调用模型、检查工具、执行工具、传回结果、继续循环”封装起来。

### 6. 工程迁移

从“网页聊天”迁移到“AI 应用”时，要分清三种能力：

```text
模型调用：生成、理解、抽取
工具调用：查知识、写记忆、读文件、调 API
应用控制：权限、审批、超时、重试、最大轮数和审计
```

Tool Use 只是连接层；工具背后的数据质量、权限和业务规则仍然由应用负责。

## 三、I1：Agent 需要什么样的数据底座

### 1. Agent 不是“把聊天记录存起来”这么简单

模型负责概率推理，数据库负责：

- 当前事实和业务状态；
- 权限、租户、发布状态；
- 检索证据和来源；
- 多步任务的一致性；
- 故障后的恢复；
- Agent 写入的隔离、差异和审批。

RAG、Memory、任务执行和业务决策都建立在数据层之上。

### 2. 判断 AI 原生数据库的六个维度

| 维度 | 要回答的问题 |
|---|---|
| 多类数据 | 关系、向量、全文、JSON、空间数据能否统一管理？ |
| 混合检索 | 语义召回、关键词召回和业务过滤能否组合？ |
| 事务与恢复 | AI 数据能否和业务状态保持一致并恢复？ |
| 模型调用 | 嵌入、重排和生成能否在靠近数据的位置管理？ |
| Agent 工作流 | 是否支持隔离试验、Diff 和受控 Merge？ |
| 交付形态 | 是否支持嵌入式、服务器、本地与跨平台？ |

“有向量字段”并不等于 AI 原生数据库；单次向量相似度也不足以满足真实业务。

### 3. 一份事实，多种表达

同一条知识记录往往同时包含：

- 关系字段：租户、负责人、状态；
- 向量字段：用于语义相似检索；
- 文本字段：用于阅读、关键词检索和引用；
- JSON 字段：保存动态元数据；
- 空间字段：支持区域和距离查询。

统一数据上下文的价值，是让权限和状态直接参与检索，减少跨系统复制、同步延迟与重复治理。

### 4. 混合检索比“只做向量”更接近生产

只做向量检索，可能漏掉型号、错误码、人名等精确词；只做关键词检索，又可能漏掉同义表达。

一条完整链路是：

```text
权限与业务条件过滤
        ↓
向量检索 + 全文检索并行召回
        ↓
RRF 或加权策略融合排名
        ↓
只对有限候选执行重排
        ↓
返回 Top-K、证据、来源和状态
```

RRF 关注候选在各通道中的排名，不要求向量距离和 BM25 分数具有同一量纲，因此通常比直接相加原始分数更稳定。

### 5. 数据库内 AI 的正确顺序

嵌入、重排和生成调用通常比普通 SQL 和索引查询更慢、更贵。合理顺序是：

> **先过滤 → 再召回 → 缩小候选集 → 最后重排或生成**

不要对整张表逐行调用模型。生产环境还要定义并发、超时、重试、预算、敏感数据边界和降级策略。

### 6. 让会写数据的 Agent 进入沙箱

Fork / Diff / Merge 把代码分支思想引入数据工作流：

- **Fork**：从主数据创建隔离分支；
- **试写**：Agent 在沙箱中修改和验证；
- **Diff**：展示新增、删除、修改和冲突；
- **决策**：由业务规则或人工审批；
- **Merge 或丢弃**：合入或放弃。

数据库事务解决“一组操作能否原子提交”；Fork / Diff / Merge 解决“AI 生成的变化能否先隔离、检查，再决定是否采纳”。两者不能互相替代。

### 7. 统一数据库还是组合式架构

- 中小规模、数据类型多、业务过滤与检索强耦合，优先评估统一数据库；
- 单一负载极大规模、确实需要专用能力，再考虑专业系统组合；
- 已有成熟数据平台和可靠同步链路时，不要为了“统一”重复建设；
- 原型只有少量静态文档，先用最简单可验证的方案；
- 本地或离线 Agent，可优先评估嵌入式数据库。

统一架构降低系统和同步复杂度，但不会自动解决索引设计、权限治理、模型成本与评测工作。

## 四、三课形成的完整方法

| 问题 | 课程 | 核心方法 | 产出 |
|---|---|---|---|
| 该不该做 Agent？ | P1 | 场景匹配 + 三维度评估 + Checklist | 立项判断和验收标准 |
| 怎么让模型做事？ | D1 | API、Streaming、Tool Use、Agent 循环 | 可运行的最小流程 |
| 怎样长期可靠？ | I1 | 统一数据、混合检索、事务、沙箱和治理 | 可追溯的数据底座 |

一个完整的任务链路应该是：

```text
用户提出目标
  ↓
P1：判断任务适合 Workflow 还是 Agent
  ↓
D1：模型理解意图并选择工具
  ↓
I1：权限过滤 → 混合召回 → 重排 → 返回证据
  ↓
D1：工具结果回到模型，生成最终答案
  ↓
审批与数据写回
```

这里最危险的做法是跳过 P1 和 I1，直接开始写 Agent 循环。因为代码可以把流程串起来，却不能创造缺失的数据，也不能替业务定义什么叫“做对了”。

## 五、迁移到活动视频项目的落地建议

对“202611 活动视频”这类项目，第一版不应直接做完全自主 Agent，而应先做可控 Workflow。

### 1. 用 P1 判断任务

适合自动化的部分：

- 根据活动脚本回答问题；
- 查找镜号、台词、素材和时间点；
- 检查名称、时长、人物和业务术语是否一致；
- 生成分镜提示词、字幕草稿和传播文案。

不应自动执行的部分：

- 未授权的素材发布；
- 最终协议和公司名称确认；
- 品牌官方素材替换；
- 高价值宣传内容未经人工审核直接上线。

### 2. 用 D1 定义最小工具集

```text
search_script(query, act_id?, shot_id?)
get_shot(shot_id)
list_assets(shot_id, missing_only?)
check_consistency(document_version)
generate_storyboard_prompt(shot_id)
```

第一版工具只读或生成草稿，发布类操作必须经过人工审批。

### 3. 用 I1 设计数据层

每条镜头记录至少保存：

```text
幕次、镜号、时间段、画面、人物、台词
业务主张、素材引用、版权状态、审批状态、版本号、来源
```

检索时应先按项目、幕次、镜号、权限和审批状态过滤，再进行向量与关键词混合召回，并在回答中返回明确出处。

### 4. 第一版验收标准

- 能准确定位“第 12 镜承诺了哪些 SLA”；
- 能列出每个镜头缺失的素材；
- 能发现服务名称出现次数或暂定名误用；
- 能对“未找到依据”的问题拒绝编造；
- 能引用幕次、镜号和来源文件；
- 所有写操作默认进入沙箱，经过 Diff 和人工确认。

## 六、课后行动清单

- 为当前项目列出 10 个典型问题和对应答案数据。
- 给每个任务标注“事实可验证”或“需要主观评估”。
- 判断第一版应该使用 FAQ、BI、Workflow 还是 Agent。
- 画出“模型判断 → 工具执行 → 结果返回 → 最终回答”的链路。
- 为每个工具写明用途、输入、输出、权限和失败处理。
- 把数据分成业务状态、知识、记忆、检索证据和任务日志。
- 在采用完全自主 Agent 前，先验证 Workflow 是否已经足够。
